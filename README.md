# 旅游地接社 - 投诉登记与补偿跟进

面向旅游地接社的投诉登记与补偿跟进系统，按「计调 → 导游/车队调度 → 主管」接力方式设计，解决投诉登记与补偿跟进之间责任不清、时效失控的问题。

## 启动方式

### 前置条件

- Node.js >= 18
- npm >= 9

### 1. 安装依赖

```bash
# 服务端
cd server && npm install

# 客户端
cd ../client && npm install
```

### 2. 启动后端

```bash
cd server
npm run dev
```

后端运行在 http://localhost:3001

### 3. 启动前端

```bash
cd client
npm run dev
```

前端运行在 http://localhost:5173，自动代理 `/api` 请求到后端。

### 4. 打开浏览器

访问 http://localhost:5173 ，选择角色进入系统。

## 数据重置

系统提供两种方式重置为初始种子数据：

1. **界面操作**：以主管角色登录，点击看板右上角「重置演示数据」按钮
2. **API 调用**：

```bash
curl -X POST http://localhost:3001/api/seed
```

## 核心业务流程

```
登记(计调) → 指派(计调) → 处理(导游/车队) → 提补偿(计调) → 审批(主管) → 执行(计调) → 关闭
```

- 投诉登记不是终点，时间线贯穿登记、处理、补偿全流程
- 被指派人首次添加备注时，状态自动从「已指派」变为「处理中」
- 主管可随时查看任意投诉的完整处理轨迹
- 主管可重新打开已关闭的投诉

## 状态机

```
registered → assigned → processing → compensating → closed
    ↑                                              |
    └──────────────── 主管重新打开 ─────────────────┘
```

- **registered**：已登记，等待计调指派
- **assigned**：已指派给导游或车队调度，等待其首次备注
- **processing**：处理中，被指派人正在添加处理备注
- **compensating**：补偿中，计调已提出补偿方案，等待主管审批
- **closed**：已关闭，补偿已执行或投诉已解决

## API 端点

| 方法   | 路径                              | 说明             | 权限              |
|--------|-----------------------------------|------------------|-------------------|
| GET    | /api/complaints                   | 投诉列表（按角色过滤） | 所有认证用户 |
| GET    | /api/complaints/:id               | 投诉详情         | 所有认证用户       |
| POST   | /api/complaints                   | 创建投诉         | 计调              |
| PATCH  | /api/complaints/:id/assign        | 指派处理         | 计调              |
| POST   | /api/complaints/:id/notes          | 添加备注         | 所有认证用户       |
| PATCH  | /api/complaints/:id/status        | 变更状态         | 按角色校验         |
| POST   | /api/complaints/:id/compensation  | 提出补偿方案     | 计调/主管         |
| PATCH  | /api/complaints/:id/compensation  | 审批/驳回补偿    | 主管              |
| POST   | /api/complaints/:id/compensation/execute | 执行补偿 | 计调              |
| GET    | /api/roles/users                  | 用户列表         | 所有认证用户       |
| GET    | /api/roles/current               | 当前用户信息     | 所有认证用户       |
| GET    | /api/health                       | 健康检查         | 无需认证           |
| POST   | /api/seed                         | 重置种子数据     | 无需认证           |

请求头 `X-User-Id` 携带用户 ID 完成身份认证。

## 哪些能力只是模拟

| 能力             | 说明                                                |
|------------------|-----------------------------------------------------|
| 用户认证         | 通过 `X-User-Id` 请求头模拟，无密码、无 Token         |
| 数据持久化       | 内存存储，服务重启后数据丢失                          |
| 权限校验         | 仅校验角色是否匹配，无细粒度资源权限                  |
| 逾期通知         | 仅界面展示逾期标记，无推送/邮件/短信通知              |
| 补偿执行         | 仅标记状态变更，无实际财务系统对接                    |
| 用户管理         | 预置4个固定用户，不支持新增/编辑/删除                 |
| 文件附件         | 时间线事件不支持附件上传                              |
| 操作日志         | 无独立的操作审计日志，仅依赖时间线记录                |
