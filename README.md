# 母婴零售店 - 退换货与客户回访管理系统

## 系统简介

这是一个专为母婴零售店设计的退换货处理与客户回访管理系统。系统核心目标是**让店员、店长、采购三方明确各自的责任，确保退换货不卡壳、客户回访不遗漏**。

## 核心功能

### 1. 智能仪表板（第一屏）
系统启动后首先展示今日待处理任务，重点回答三个问题：
- **谁在处理？** - 明确显示店员、店长、采购各自的待办任务
- **退换货卡在哪里？** - 超过3天的退换货自动标记"卡住"，显示具体原因
- **客户回访为什么还没完成？** - 逾期未完成的回访自动标记，显示卡住原因

### 2. 退换货处理流程
- **类型**：退货、换货
- **原因分类**：质量问题、发错商品、运输损坏、过期商品、会员要求、其他
- **状态流转**：待处理 → 店员审核 → 店长审批 → 采购处理 → 已完成/已拒绝
- **关键信息**：
  - 当前应该谁处理（current_handler_role）
  - 卡住原因（stuck_reason）
  - 批号追溯（ProductBatch）

### 3. 客户回访管理
- **回访方式**：电话、短信、微信、到店
- **优先级**：高、普通、低
- **状态**：待回访、回访中、已完成、回访失败、已跳过
- **关联**：可以关联到具体的退换货记录

### 4. 审计日志
- 记录所有操作的历史
- 支持按实体类型、操作类型、时间范围筛选
- 记录旧值和新值，便于追踪变更

### 5. 导出功能
- 支持导出退换货记录、客户回访记录、审计日志
- 导出格式：Excel（.xlsx）
- 包含完整业务信息

### 6. 消息通知
- 站内通知
- 支持创建、标记已读等功能
- 可扩展到邮件、短信（预留接口）

### 7. 附件管理
- 支持图片、文档等附件
- 与退换货记录、客户回访关联

## 技术栈

- **后端框架**：Django 4.2 + Django Ninja 0.21
- **数据库**：SQLite 3（开发环境）
- **导出功能**：openpyxl
- **认证**：Django 内置认证系统

## 快速开始

### 1. 安装依赖

```bash
pip install -r requirements.txt
```

### 2. 初始化数据库

```bash
python manage.py migrate
```

### 3. 创建种子数据

```bash
python manage.py init_seed_data
```

这将创建：
- 4个员工账号（2名店员、1名店长、1名采购）
- 7个商品（奶粉、尿裤、辅食、玩具、用品）
- 5个会员档案
- 4条退换货记录（包含卡住的案例）
- 4条客户回访记录（包含逾期未完成的案例）
- 若干审计日志

### 4. 启动服务器

```bash
python manage.py runserver
```

### 5. 访问API文档

打开浏览器访问：http://127.0.0.1:8000/api/docs

## API接口说明

### 仪表板
- `GET /api/store/dashboard` - 获取今日待处理任务

### 退换货
- `GET /api/store/returns` - 查询退换货列表
- `GET /api/store/returns/{id}` - 获取退换货详情
- `POST /api/store/returns` - 创建退换货
- `PUT /api/store/returns/{id}` - 更新退换货

### 客户回访
- `GET /api/store/visits` - 查询回访列表
- `GET /api/store/visits/{id}` - 获取回访详情
- `POST /api/store/visits` - 创建回访
- `PUT /api/store/visits/{id}` - 更新回访

### 审计日志
- `GET /api/store/audit-logs` - 查询审计日志
- `GET /api/store/audit-logs/export` - 导出审计日志

### 导出
- `GET /api/store/returns/export` - 导出退换货记录
- `GET /api/store/visits/export` - 导出回访记录

### 其他
- `GET /api/store/notifications` - 获取消息通知
- `GET /api/store/employees` - 获取员工列表
- `GET /api/store/members` - 获取会员列表

## 数据模型说明

### Employee（员工）
- `role`：角色（clerk/manager/purchaser）
- 判断权限的方法：`can_handle_returns()`、`can_approve_returns()`、`can_handle_purchasing()`

### ReturnExchange（退换货）
- `current_handler_role`：当前应该处理的人（clerk/manager/purchaser）
- `stuck_reason`：如果卡住，记录原因
- `get_stuck_info()`：返回是否卡住及详细信息

### VisitRecord（客户回访）
- `stuck_reason`：如果未完成，记录原因
- `get_stuck_info()`：返回是否逾期及详细信息

### AuditLog（审计日志）
- 记录所有业务操作的变更历史
- 支持操作类型：create、update、delete、status_change、assignment、approval、rejection等

## 典型业务场景

### 场景1：奶粉质量问题退换货
1. 会员陈妈妈到店反映购买的奶粉有结块
2. 店员张晓丽创建退换货单（RE202406150001）
3. 系统自动分配给店员处理
4. 店员确认质量问题，状态变为"店员审核中"
5. 店长审批通过，状态变为"店长审批中"
6. 店长审批通过，状态变为"采购处理中"
7. 采购刘处理完成，退款给会员
8. 完成后创建客户回访，确认满意度

### 场景2：逾期未完成的客户回访
1. 店员创建回访任务（VIS202406150001）
2. 计划回访日期为2天前
3. 系统检测到逾期，标记为"卡住"
4. 显示卡住原因："店员表示客户电话无人接听，需要改时间联系"
5. 店员更新回访状态或修改计划时间

## 设计原则

1. **责任明确**：每个退换货和回访都明确分配给具体的人
2. **流程透明**：状态流转清晰，可以追踪每个节点
3. **问题可见**：卡住的任务自动标记，显示原因
4. **可追溯**：完整的审计日志，记录所有操作
5. **实用为主**：导出、附件、通知等辅助功能完善但不冗余

## 注意事项

- 种子数据包含一些"卡住"的案例，用于演示系统如何帮助发现和处理问题
- 导出功能记录审计日志，便于追踪数据导出行为
- 消息通知目前只实现站内通知，邮件和短信接口已预留
- 所有API都需要Django认证，可以通过Django admin创建超级用户来管理
