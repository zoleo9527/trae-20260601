# 医美机构 - 术后回访与不适上报系统

## 核心设计：过程可追溯

一线处理和管理回看基于**同一份数据**。咨询记录、方案报价单、术后回访表不仅记录**结果**，更记录**为什么变**。

- 每一次修改都必须填写「变更原因」
- 每一条数据都有「版本号」和「版本历史」
- 每一个状态变更都记录「谁、什么时候、做了什么」
- 不适/投诉从上报到结案，**处理流程全程留痕**

### 1. 术后回访处理

**入口**：左侧导航 →「术后回访」

**密集表格字段（10列）**：
| 列 | 说明 |
|----|------|
| ID | 回访记录唯一编号 |

- 版本号 + 修改时间 + 修改人

## 二、核心追溯机制

### 数据模型设计

```
Customer ──1:N──> ConsultationRecord ──1:N──> ConsultationRecordVersion
   │
   ├──1:N──> QuotationScheme ──1:N──> QuotationSchemeVersion
   │                            └── 分期款项、承诺服务、项目明细
   │
   ├──1:N──> PostOperativeFollowUp ──1:N──> FollowUpVersion
   │                            └── 恢复状态、异常症状、处理建议
   │
   └──1:N──> DiscomfortReport ──1:N──> HandlingRecord
                                    └── 每一步处理都留痕

AuditLog ── 全局审计，所有实体的所有变更
```

### 强制约束

1. **任何更新必须填写变更原因**
   - API 层 `change_reason` 字段必填
   - 版本表强制记录变更原因

2. **版本号自动递增**
   - 每次更新 `current_version += 1`
   - 保存完整快照到版本表

3. **不适处理必须更新状态**
   - 每次处理必须指定 `new_status`
   - 自动记录 `previous_status`
   - 状态流转：待处理 → 处理中 → （已升级） → 已关闭

## 三、API 接口速查

| 模块 | 接口 | 说明 |
|------|------|------|
| 咨询记录 | `GET /api/consultation-records/{id}/versions` | 版本追溯 |
| 方案报价 | `GET /api/quotation-schemes/{id}/versions` | 版本追溯（含分期变更） |
| 术后回访 | `GET /api/follow-ups/{id}/versions` | 版本追溯 |
| 不适上报 | `GET /api/discomfort-reports/{id}/handling-records` | 处理流程回看 |
| 不适处理 | `POST /api/discomfort-reports/{id}/handle` | 新增处理记录 + 更新状态 |
| 全局审计 | `GET /api/audit-logs` | 所有操作日志 |

## 五、真实场景覆盖

✅ **承诺口径不一致问题可查**：咨询记录版本对比，看每次怎么说的

✅ **分期款项对不上可查**：报价方案版本追溯，每次改价原因一清二楚

✅ **术后投诉可追溯**：从第一次回访发现异常 → 上报 → 每一步谁处理、说了什么、下一步是什么，完整时间线

✅ **一线和管理层基于同一数据**：所有人看的是同一条记录的同一版本，历史版本随时可查
